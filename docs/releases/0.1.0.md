# Preflight 0.1.0

Preflight 0.1.0 is the first public beta of a free, open-source performance launcher and companion app for Starsector. It prepares repeatable startup work ahead of launch, binds reusable work to the inputs that produced it, and falls back to the original game path whenever an optimization cannot prove that its reviewed conditions still hold.

> Preflight is an independent, unofficial project. It isn't affiliated with or endorsed by Fractal Softworks.

These are tag-owned release notes. They contain only facts that are knowable before the release tag is created. Package-dependent lifecycle, startup-benchmark, and report-intake evidence is produced from the exact tagged candidate afterward and is reviewed as separate release evidence before publication; those post-tag results are deliberately not guessed into this file.

## Performance

On the reviewed 83-mod development installation, the latest same-profile controlled comparison measured:

- **89.00-second median** across five ordinary launches;
- **15.53-second median** across five Preflight launches in the same session;
- **15.25 seconds** for the lowest recorded Preflight launch in that comparison;
- roughly **101 seconds** as an earlier observed development high.

The controlled session interleaved the two conditions, cooled the machine for 240 seconds before each launch, and excluded none of the ten runs. Those values describe one M5 MacBook Air, one 83-mod profile, Starsector 0.98a-RC8, and the stated development runtime conditions. They are not a claim about the tagged package.

The release gate separately requires a startup benchmark through the verified engine extracted from the exact tagged candidate package. That receipt is post-tag evidence and is tracked with the release-readiness record instead of being predeclared here.

The desktop also includes a normal-versus-Preflight benchmark so each installation can measure its own result. **Copy result** produces a bounded shareable summary without copying raw evidence or private paths.

## What is included

### Prepared startup work

Recommended mode is the default. A fresh profile starts with complete Balanced texture coverage;
after one successful launch, Preflight learns the access order and prepares the smaller Compact
steady state during a later idle window. Preflight can also prepare reusable data, generated-code,
and audio work before Starsector launches. Matching work is reused automatically; stale, damaged,
missing, unsupported, or unfamiliar inputs use the original path.

The three user-facing optimization levels are:

- **Recommended** — every optimization enabled for the exact inputs it recognizes;
- **Conservative** — broad immutable-input startup caches without the more specialized runtime shortcuts;
- **Off / troubleshooting** — runtime transformations and profiling disabled while the launcher, profiles, settings, support, and process-management features remain available.

### Named mod profiles and launch settings

Profiles can be created, searched, switched, renamed, duplicated, and deleted. Switching previews the enabled-mod change and saves a backup before applying it.

Resolution, fullscreen, sound, antialiasing, UI scale, RAM, and battle size are available beside Launch. Memory changes follow the selected launcher to one unambiguous launcher-owned settings file and keep a backup. Ambiguous layouts are refused instead of guessed.

### Storage planning, cleanup, and recovery

Before preparation, Preflight calculates the current build's temporary and finished storage, current free space, compatible data already retained, selected loose data that can actually be reused, and exact current-profile pack reuse when the builder can prove it. Raw codec ceilings remain internal instead of being presented as a second player-facing requirement.

Cleanup is preview-first. Current and readable named profiles remain reachable, and Starsector, mods, and saves are outside the cleanup target. Preparation can stop safely; completed immutable work remains usable, while an incomplete new manifest is never activated.

### Playtime and launch history

Preflight keeps a bounded local launch-history ledger for sessions it owns and can observe. The ledger is separate from larger diagnostic run directories so old diagnostic evidence can be pruned without forgetting that a launch happened. Historical backfill and interrupted-session recovery are best-effort and identity-checked.

### Read-only setup analysis

`preflight lint` reports measurable asset and configuration problems without editing the installation or assigning a score. `preflight scan` inventories the enabled profile. The deeper setup analysis can report missing or malformed mod metadata, duplicate IDs, missing or disabled required dependencies, and resolved variants whose declared hull is absent from the active profile.

### Privacy-conscious support

**Copy setup** produces bounded support text without paths, credentials, save contents, or arbitrary logs.

The separate support ZIP uses a fixed allowlist and explicit size limits. It excludes acceleration caches, Starsector and mod files, saves, screenshots, audio, arbitrary logs, crash dumps, JFR recordings, credentials, and unknown files. Where the release intake is enabled, the desktop discloses the exact ZIP before sending, supports cancellation and retry, and presents the accepted case receipt and deletion option without exposing the deletion bearer credential to the renderer.

The first beta does not send failed-run reports automatically.

### Signed updates and rollback

Supported updater packages use one fixed release feed. The user reviews a newer release and chooses **Install and restart**; the exact reviewed offer is rechecked and the updater signature is verified before installation. Cache formats use versioned namespaces so rollback does not require rewriting every older representation in place.

Linux `.deb` installations remain package-manager-managed.

## Packages and release trust

The first beta targets:

- **Windows x86-64** — `Preflight-Windows-x86_64.exe` (NSIS installer);
- **macOS Apple silicon** — `Preflight-macOS-arm64.dmg`;
- **Linux x86-64** — `Preflight-Linux-x86_64.AppImage` and `Preflight-Linux-x86_64.deb`;
- the standalone `preflight.jar`, `.zip`, and `.tar.gz` distributions.

Native packages include the minimal Java runtime used by Preflight. Starsector and Fast Rendering continue to use their own runtime.

The complete Distribution set also carries SHA-256 manifests, dependency inventory, target-specific CycloneDX SBOMs and their checksums, license and third-party notices, privacy information, known limitations, updater artifacts, and the fixed update manifest.

The first beta does not use paid Apple Developer ID or Windows Authenticode publisher identities, so macOS and Windows can show their normal unknown-developer warnings. Preflight's updater signature is separate from those platform publisher identities.

Creating the tag produces a draft release and the exact candidate bytes. Package lifecycle, exact packaged-engine benchmark, report-intake canary, and the remaining release checks are then run against those tagged bytes. Publication must use the already-created draft and its verified assets; a rehearsal candidate or a rebuild with the same source revision is not the final package authority.

## Known beta limits

- Real-game testing has been deepest on Apple silicon macOS. Windows and Linux have substantial automated package coverage; the first beta is published only after the required real-game Windows and Linux installation exercises complete.
- There is no Intel Mac package in the first beta.
- The reviewed game version is **0.98a-RC8**. Other versions may use fewer optimizations until changed targets are reviewed.
- The development performance numbers above describe the stated machine and 83-mod profile; other installations can differ substantially.
- On the 83-mod development profile, first preparation measured about 38 seconds in Balanced and
  17 seconds in Compact. The app measures the local storage requirement before starting.
  Preparation time varies with the installed content and machine.
- Runtime adapters are exact-gated. A changed or unknown target loses that optimization and retains the original game behavior.

See [Known limitations](../known-limitations.md) for the complete list and [Release readiness](../release-readiness.md) for the release-evidence checklist.
