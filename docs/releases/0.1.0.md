Preflight 0.1.0 is the first public beta of a free, open-source performance launcher for Starsector.
It prepares repeatable work ahead of launch, binds that work to the exact game and ordered mod inputs
that produced it, and reuses it while those inputs still match. Runtime shortcuts are checked
against the code they were reviewed against and fall back to the original game path on uncertainty.

The project began as a loading-time investigation and ended up becoming a much broader Starsector
desktop and power-user tool.

## Performance

On the reviewed 83-mod development installation, the latest same-profile controlled comparison
measured:

- **89.00-second median** across five ordinary launches;
- **15.53-second median** across five Preflight launches in the same session;
- **15.25 seconds** for the lowest recorded Preflight launch in that comparison;
- roughly **101 seconds** as the earlier observed development high.

The controlled session interleaved the two conditions, cooled the machine for 240 seconds before
each launch, and excluded none of the ten runs. Those numbers describe one M5 MacBook Air, one
83-mod profile, Starsector 0.98a-RC8, and the stated runtime conditions.

The desktop includes the same normal-versus-Preflight startup benchmark so each installation can
measure its own result. **Copy result** produces a bounded shareable summary containing the two
measured startup times and an installation-specific qualifier without copying raw evidence or
private paths.

The Speed page also keeps a local **Personal best** and the **Latest benchmark** with their recorded
dates and normal→Preflight split. Personal best remains the trophy when a later result is worse, but
Latest always becomes the newest controlled pair; an unfavorable new measurement is not hidden just
because an older one looked better.

Preflight deliberately does **not** turn one controlled benchmark into a running lifetime “time
saved” counter for later ordinary launches. An ordinary launch currently carries weaker identity
evidence than the controlled benchmark pair. Earlier local-history logic tried to bank those derived
savings and was removed rather than keep displaying a satisfying number that the later launch could
not prove was benchmark-comparable.

## What is included

### Prepared startup work

Recommended mode and Balanced storage are the defaults. Preflight can prepare reusable texture,
merged/spec-data, generated-bytecode, audio, and related startup inputs before the game launches.
Matching work is reused automatically; stale, damaged, missing, or unfamiliar inputs use the
original path.

Three user-facing optimization levels keep troubleshooting simple:

- **Recommended** uses every optimization that passed its live correctness gate;
- **Conservative** keeps broad immutable-input startup caches while omitting mod-specific/gameplay
  runtime shortcuts;
- **Off / troubleshooting** disables runtime transformations and profiling while keeping the wrapper,
  process handling, profiles, settings, support, and other launcher functionality available.

### Starsector playtime tracking

Preflight keeps a durable local total for sessions it launches and can observe, including when the
desktop minimizes or exits after starting the game. The UI shows total/session context and can copy a
bounded playtime summary. The engine can export versioned JSON with an optional spreadsheet-safe CSV
view.

### Named mod profiles

Profiles can be created, searched, switched, renamed, duplicated, and deleted. Switching previews the
exact enabled-mod change and saves a backup before applying it. Duplicating a profile does not copy
mods, saves, or prepared data.

The switch review shows the concrete mods that will be enabled and disabled before anything changes.
Saved profiles retain their mod count and save time, and the UI can flag a profile from a different
installation or one whose required installed mods are currently missing.

### Launch settings

Resolution, fullscreen, sound, antialiasing, UI scale, RAM, and battle size are available beside
Launch.

The battle-size presets can extend past the ordinary vanilla slider while still using Starsector's
own `battleSize` preference. On an ordinary installation the current shortcuts include 600, 1000,
1500, and 2000 deployment-point choices. If an installed mod changes the normal limits, Preflight
derives the anchors from that installation instead of pretending the vanilla numbers still apply.

Resolution choices use the physical panel pixels behind OS display scaling, so a high-DPI desktop
is not artificially limited to its scaled logical resolution.

RAM changes follow the selected launcher to one unambiguous launcher-owned `vmparams` file, keep an
exact backup of the original, and refuse ambiguous layouts instead of guessing which memory setting
the game will actually use.

### Storage planning and cleanup

Preflight calculates the selected profile before preparation, including predicted additional data,
a conservative safety bound, reusable artifacts, and current free space. It keeps a reserve and
refuses before writing when the safe bound does not fit.

On the reviewed 83-mod development profile, one cold-preparation measurement retained 4.76 GB for
Balanced, 10.9 MB for Minimal disk, and 10.03 GB for Fastest. These are reference-profile numbers,
not universal requirements; the desktop calculates the local plan.

Cleanup is preview-first and keeps current/readable named profiles reachable. App-only removal and
removal of all Preflight-owned data are separate choices. Neither includes Starsector, mods, or
saves.

Long-term housekeeping is part of the same model. Launch reports and benchmark sessions have their
own retention policy because deleting evidence cannot affect launch speed. The visible **Free space**
action keeps the newest 10 launch reports and 5 benchmark sessions, shows acceleration and evidence
separately, and recalculates the complete plan immediately before deletion.

Once the complete Preflight cache grows beyond 12 GiB, the desktop can also attempt one quiet
fail-closed prune while idle. Current and named profiles survive, shared reachable blobs remain, and
an unsafe or incomplete plan removes nothing. Failure is nonblocking and the visible **Free space**
review remains the retry path.

### Recovery and repair

Preparation has progress and safe-stop behavior. Interrupted work keeps completed immutable data
reusable without activating an incomplete new manifest. Structurally damaged prepared data can be
repaired for the exact profile. Failed runs expose Relaunch, **Copy setup**, Get help, and Dismiss on
Home.

### Privacy-conscious support

**Copy setup** produces bounded support text containing useful game/profile/mod/launch facts without
paths, credentials, save contents, or arbitrary logs.

The separate support ZIP uses a fixed allowlist and explicit size limits. It excludes acceleration
caches, Starsector and mod files, saves, screenshots, audio, arbitrary logs, crash dumps, JFR
recordings, credentials, and unknown files. The desktop discloses the exact ZIP before sending and
supports progress, cancellation, retry, case receipt, retention information, and deletion where the
release intake is enabled. The accepted receipt binds the uploaded digest and size; the supported
intake path can use its scoped authorization to delete that exact uploaded report early.

Automatic failed-run reporting is a separate remembered setting and starts off.

### Signed updates and rollback

Supported updater packages check one fixed release feed and present newer releases for review. The
user must choose **Install and restart**. Before installation, Preflight rechecks the exact offer that
was reviewed, and Tauri verifies the updater signature. A failed download, verification, or
installation leaves the current version runnable.

Linux `.deb` installations remain package-manager-managed.

Incompatible cache formats use separate namespaces instead of rewriting every older representation
in place. That allows an older Preflight release to keep using the format it understands after a
rollback; broader cleanup remains the user's explicit choice.

### Compatibility after game and mod updates

A Preflight application version, the exact game/mod identities it recognizes, and the current mod
profile are separate things.

Prepared content validates the inputs that determine its answer. Generic prepared paths can continue
to work wherever those exact inputs still satisfy their contract. Runtime adapters are pinned to the
specific reviewed code they transform. If one game or mod target changes, that adapter declines and
the original game path handles that work instead of applying an older transformation because a class
still has the same name.

A large enough game, launcher, classloading, preference, or runtime change can still require a new
Preflight application release. The practical point is that one changed mod does not automatically
turn every prepared artifact and every other optimization into invalid state.

Preflight also respects known third-party ownership. For example, when Fast Rendering's custom loader
owns the reviewed Janino compiler path, Preflight leaves that compiler seam to Fast Rendering rather
than trying to double-own it.

### Read-only mod linting and profile analysis

`preflight lint` can inspect one mod or a whole profile for measurable asset/configuration problems
without editing anything or assigning a score. The current rules include progressive-image decode
cost, large NPOT padding, oversampled/long/unreferenced audio, missing sounds, shadowed/duplicate
assets, editor source files, extension mismatches, and configuration that cannot be parsed or that
sits after the value the game actually reads.

On the reviewed corpus, progressive JPEGs decoded about 8.75 times slower through the game's ImageIO
path than equivalent baseline encoding. Calibration across 86 installed mod directories produced a
median of zero findings and 44 of 86 completely clean.

`preflight scan` is a separate profile census. It reports enabled and missing mod IDs, total files and
bytes, images, sounds, JARs, loose Java, per-extension and per-mod totals, largest assets/mods,
duplicate logical paths, and provider-order winners.

`preflight analyze setup` is a deeper read-only setup check. It does not launch or modify Starsector.
It can report enabled mods with missing/invalid metadata, duplicate installed mods declaring the same
ID, required dependencies that are missing or installed-but-disabled, malformed dependency
metadata, and winning variants whose declared hull is absent from the resolved profile. It can emit
the result as JSON for tooling.

### Power-user launch tools

The desktop and CLI use the same Java engine and core safety checks.

- `preflight doctor` discovers launchers and shows the selected candidate without starting the game.
- `--dry-run` prints the exact selected launcher, complete command, working directory, trace
  destination, adapter mode, and injected Java option without starting Starsector.
- Preflight can wrap the ordinary launcher, Fast Rendering launcher names, or an explicitly selected
  compatible wrapper instead of replacing those files on disk.
- The optional direct-launch path uses Starsector's own `launchDirect` behavior and saved launch
  preferences to skip the launcher UI. It refuses malformed/unavailable saved settings instead of
  guessing.
- The standalone JAR remains available alongside the native desktop packages.

### A Starsector-adjacent Hangar without bundled game art

The desktop's wireframe ship presentation is reconstructed locally from the installed game. The
native host reads bounded hull definitions and traces featured installed sprites into new wireframe
contours for the UI. Preflight does not need to ship copied Starsector sprite artwork to make the
Hangar feel connected to the game.

The selected display hull is remembered. Wireframe smoothing, outer/interior detail, and depth can be
tuned per installation and hull, so the Hangar is an actual cosmetic preference rather than a fixed
screenshot baked into the application.

Preflight also has five color palettes — **Blueprint, Hangar, Ultraviolet, Airglow, and Phosphor** —
on top of System, Light, and Dark theme choices. Home itself can use the full hull-led Hangar
presentation or a Compact launch-first view; recorded playtime visibility and hull motion/direction
are independent display preferences.

### Get out of the way after launch

After Preflight has verified that the actual Starsector JVM is alive, a remembered preference decides
what happens to the desktop window: **Minimize**, **Keep open**, or **Quit**. Minimize is the default.
If the player chooses Quit, the local playtime ledger still records the Starsector session.

That gives the desktop a useful lifecycle: do the setup/launch work, then disappear if the player
wants it to.

## What Preflight leaves alone

Preflight does not permanently patch Starsector or mod JARs, executables, assets, activation data, or
saves. Runtime changes exist only inside the launched game JVM and disappear when it exits.

Two explicit backed-up actions can update game-owned preferences:

1. named-profile activation changes the enabled-mod selection after preview;
2. the launch-settings editor changes the corresponding reviewed game/launcher settings.

Prepared data, benchmarks, playtime evidence, and other Preflight state live under Preflight-owned
locations.

The desktop host exposes a fixed set of typed native commands; the renderer does not receive an
arbitrary shell. A stop action is tied to the recorded process identity, including its start time, so
a reused PID or unrelated Starsector process is left alone.

## Package and release trust

**Release platforms:** [FINAL PACKAGE MATRIX]

The native desktop packages contain their own minimal Java runtime for Preflight. Using the desktop
app does not require installing a system JDK. Starsector and Fast Rendering continue to use their own
runtime.

The first beta does not use paid Apple Developer ID or Windows Authenticode publisher identities, so
macOS and Windows may show their normal unknown-developer warning. Every native download is paired
with a SHA-256 manifest.

Preflight's updater signature is separate from those platform identities. The release process also
verifies complete artifacts and exercises package installation, upgrade, rollback, and removal.
Every native package carries a machine-checked capability receipt that records its reviewed native
commands, writes, child processes, links, and network endpoints and binds that statement to the
actual package/update artifact hashes.

The planned public release also includes license and third-party notices, privacy and known-limitations
material, dependency inventory, target-specific CycloneDX SBOMs, and checksums for those inventories.
Those files are there so a skeptical user or developer can inspect the release without treating the
installer as a black box.

The first beta also deliberately avoids a second remote code-delivery path for runtime
transformations. New executable transformation logic ships through signed application releases;
future remote compatibility advisories may narrow or disable a known-bad plan, but should not be a
way to inject new transformation code into an installed client.

## Known beta limits

- Real-game testing has been deepest on Apple silicon macOS.
- Windows and Linux have substantial automated package/lifecycle coverage; broader real-machine
  Starsector evidence continues during the beta.
- There is no Intel Mac package in the first beta.
- The reviewed game version is **0.98a-RC8**. Other versions can use fewer optimizations until changed
  targets are reviewed.
- Development performance numbers describe the stated machine and 83-mod profile. Other installations
  can differ substantially.
- First preparation can take several minutes and gigabytes on a large profile. The app calculates the
  local requirement before starting.

See [Known limitations](../known-limitations.md) for the complete list.
