# What Preflight stores, and what the storage buys

**Status:** current design reference

**Profile for measured sizes:** Starsector 0.98a-RC8 with 83 enabled mods

**Updated:** 2026-08-07

Preflight moves stable work out of the launch and into checked artifacts. That exchange is the
source of most of its speed. Disk use is a visible, reversible product choice.

The default policy is **Balanced**. On the development profile it keeps most of the prepared-texture
benefit in about 2.26 GB. **Fastest** spends another 3.08 GB to save roughly 446 milliseconds at the
exact texture-read seam. Both policies are lossless and reconstruct the same upload-ready RGB/RGBA
bytes.

## Current choices

| Area | Balanced or default behavior | Larger or more aggressive choice | What changes |
| --- | --- | --- | --- |
| Prepared textures | Hybrid raw/LZ4, about 2.259 GB | Raw Fastest pack, about 5.338 GB | Fastest saves about 446ms at the exact replay seam for about 3.08GB |
| Prepared audio | Exact decoded PCM, about 1.1 GB on this profile | Prepare fewer sounds or disable the audio cache | Less disk returns Vorbis decode and CPU work to launch |
| Generated bytecode | Deduplicated complete-map pack, about 1.13 MiB for the measured context | Retain old per-request bundles and stale contexts | No speed benefit; safe prune can remove proven duplicates |
| Cache repair | Keep checked loose artifacts beside the active pack | Remove only unreachable representations after a prune plan | Redundancy allows repair and fail-open fallback |
| Diagnostics | Keep reports, logs, and selected benchmark archives | Export or remove evidence separately from acceleration data | Evidence uses a separate storage category |
| Runtime concurrency | Bounded preparation and profile-selection pools | Serial kill switch on constrained systems | More overlap uses more simultaneous CPU, I/O, and memory |

These measurements come from the current profile. A small vanilla profile will prepare much less
data; a large mod set with high-resolution art or many sounds may prepare more. The desktop app
should show an estimate from the discovered profile.

## Why Balanced is hybrid

The first Balanced implementation stored every prepared texture with lossless LZ4. Across 30,639
unique prepared arrays, that reduced 5.335 GB of raw pixels to 2.201 GB, a 58.8 percent saving. Its
five-launch median was 23.15 seconds beside a 23.08-second raw median, a 70-millisecond difference
well below ordinary launch noise. The cohort found no measurable whole-launch regression from
lossless compression. The corpus, codec, and launch evidence is in
[the original Balanced report](evidence/2026-08-06-balanced-texture-storage.md).

Some images barely compress, so spending Rosetta CPU time on them bought almost no disk space. A
threshold sweep selected a 1.30 compression ratio as the compact knee: 3,440 blobs remain raw and
27,198 use LZ4, producing a 2,258,964,304-byte pack. The hybrid is only 54.9 MB larger than all-LZ4,
and an exact alternating-process replay improved by another 55.6 milliseconds at the prepared-pack
read seam. The threshold and learned-order correction are documented in
[the hybrid-pack report](evidence/2026-08-06-balanced-hybrid-texture-pack.md).

Fastest remains useful for users who value every measured fraction of a second more than disk. Ten
shuffled fresh-game-JVM passes replayed the same 14,774 successful startup accesses and restored the
same 2,074,073,333 output bytes and checksum:

| Texture representation | Pack bytes | Median exact replay |
| --- | ---: | ---: |
| Balanced comparison pack | 2.214 GB | 1,137.457ms |
| Fastest raw pack | 5.338 GB | **691.143ms** |

The 446.314-millisecond improvement is causal at that seam. The corresponding real launch served as
an integration gate. The interface can describe Fastest as “about 3.08 GB more for a measured
sub-second texture-read improvement on the reference profile,” then show a local estimate when one
is available.

## Why Balanced uses LZ4

Zstandard compressed the texture corpus to 1.635 GB and decoded it in 5.318 seconds on the game's
x86 JVM under Rosetta. LZ4 produced 2.197 GB and decoded in 1.533 seconds. Preparation encoding took
21.743 seconds with Zstandard and 5.451 with LZ4. Balanced uses LZ4.

| Codec on the measured corpus | Stored bytes | Rosetta encode | Rosetta decode |
| --- | ---: | ---: | ---: |
| Raw | 5.332 GB | — | — |
| LZ4 | 2.197 GB | 5.451s | 1.533s |
| Zstandard | 1.635 GB | 21.743s | 5.318s |

A future maximum-compression tier could expose Zstandard explicitly. The file format and pure-Java
implementation are portable; the timing above comes from the reviewed Rosetta environment and will
vary with CPU speed.

## Prepared audio has a different space curve

Prepared audio occupies about 1.1 GB because it stores decoded 16-bit PCM. Unlike the texture
corpus, representative PCM was effectively incompressible: a 44,810,424-byte sample became
44,810,483 bytes under LZ4 and 44,241,512 under Zstandard. Compression recovers almost no space and
adds a decode stage.

The available choices are to prepare the sound, prepare selected sounds, or let the game decode it
on each launch. Preparation removed substantial Vorbis CPU work and a measured wait in earlier
profiles. The later path index and trusted reader removed repeated hashing and heap copies. The
current representation and alternatives are described in
[the cache-space report](evidence/2026-08-05-cache-space-budget.md),
[the path-index report](evidence/2026-08-05-prepared-audio-path-index.md), and
[the direct-read report](evidence/2026-08-06-prepared-audio-direct-read.md).

A lower-space preset should expose selective preparation as an independent choice. It needs a
measured policy before becoming a public option.

## Some later caches became smaller as well as faster

Janino's early complete-map cache retained hundreds of per-request bundles, each repeating much of
the same generated bytecode. Content deduplication reduced a roughly 145.96 MiB context to a 1.13
MiB pack and changed a warm read seam of about 1.5 seconds into a 29–38-millisecond read.

Old bundles and compiler contexts remain until their relationship to the active pack can be proven.
The prune operation reads both checksummed forms and removes a bundle only when the active pack
contains the same request and byte-identical complete class map. The first real plan identified 693
files and 505 MB as reclaimable. See
[the Janino pack report](evidence/2026-08-05-janino-deduplicated-pack.md) and
[the cache-space report](evidence/2026-08-05-cache-space-budget.md).

## Redundancy is part of the failure model

The active texture pack can coexist with its loose SPFT artifacts. Loose checked blobs support
repair, format switching, and safe fallback when a pack is absent or malformed. A new
manifest is published only after preparation succeeds, and old profile or storage representations
remain recoverable until an explicit prune proves that the current manifests don't reach them.

This can temporarily make the cache look much larger than the selected policy. On the development
machine, a point-in-time read-only inventory reported 21.79 GB under the Preflight home, split into
11.61 GB of acceleration data and 10.18 GB of evidence. The current-profile prune preview could
reclaim 5.82 GB across 31,338 files, chiefly 5.28 GB of old texture representations. Those figures
describe a heavily instrumented development installation with multiple historical formats. A new
user installation will have a different footprint.

The product should show these categories separately:

- **Active acceleration:** artifacts reachable from the selected game, mod profile, and policy.
- **Fallback and repair:** checked redundant forms retained for safe recovery.
- **Other profiles and versions:** valid acceleration data outside the active profile.
- **Evidence:** benchmarks, diagnostics, reports, recordings, and exported support bundles.
- **Reclaimable:** data proven unreachable by a completed dry-run plan.

`preflight cache prune` is a read-only plan. `preflight cache prune --yes` applies that exact plan
only after reachability is complete; an unknown profile, unreadable manifest, damaged pack, or
identity mismatch retains data. The GUI should preserve the same two-step
contract and state how much will be removed before asking for confirmation.

## CPU, memory, and temperature are also resources

Preparation hashes resources, decodes media, compresses selected textures, and builds indexes.
Independent stages overlap within a concurrency bound. This uses available cores and protects
lower-memory systems from swap pressure. Every concurrent path needs a serial fallback or a small
configurable cap.

This matters particularly on the reference MacBook Air, where the game and its bundled x86 JVM run
under Rosetta and the machine has no fan. Removing CPU work outside the current launch's critical
path can still reduce heat, subsequent contention, and back-to-back throttling. Unbounded CPU use
and allocation can lose on constrained hardware even after winning a single desktop benchmark.

The deep texture validator reserves decoded size against its memory budget, preventing several
highly compressible images from expanding concurrently beyond the configured limit. Profiling also
has its own resource policy: a single-chunk startup recording uses a bounded 256 MiB buffer. Ordinary
before/after comparisons use timing mode.

## Lossy GPU blocks remain experimental

BC1/BC3 preparation remains experimental. On the corpus where it was baked, eligible textures were
about 4.51 times smaller than raw pixels, with projected GPU
memory near one quarter of the uncompressed representation. The result is lossy and requires
per-texture fidelity gates. An accepted runtime consumer is still missing.

It remains a separate opt-in experiment pending visual comparisons, cross-driver behavior, and a
real runtime path. The capability and fidelity work is retained in
[the macOS GL probe](evidence/2026-07-25-macos-gl-capability-probe.md),
[the first real profile run](evidence/2026-07-26-first-real-profile-run.md), and
[the encoder/driver agreement report](evidence/2026-07-26-encoder-driver-byte-agreement.md).

## Product behavior implied by the measurements

The first-run experience should present a local estimate, select Recommended runtime behavior and
Balanced storage by default, and explain that preparation can be interrupted safely. Fastest should
remain a simple optional switch. Audio can be shown as a separate storage contributor because its
tradeoff differs from textures.

That estimate now comes from the resolved winning texture set rather than the installation's encoded
size. It hashes content for deduplication, reads dimensions and alpha channels without decoding the
whole cold corpus, recognizes fully checked reusable blobs and an exact profile pack, and reports a
prediction beside a raw-size upper bound. The reviewed cold profile predicted 4.91 GB against an
observed approximately 4.53 GB footprint. Its upper bound was 11.74 GB, with another 1.17 GB kept
free as a reserve. The CLI enforces the same calculation before writes, so the desktop display isn't
the safety boundary.

After preparation, the app should show active acceleration, other valid profiles, evidence, and the
current safe-prune estimate. Switching a profile or storage policy publishes a new manifest only
after the new representation is ready, so the existing launch remains usable if preparation fails.
Uninstalling or choosing Off stops using the artifacts; deleting them is a separate explicit and
recoverable storage decision.
